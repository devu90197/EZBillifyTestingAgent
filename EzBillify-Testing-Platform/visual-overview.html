EzBillify Testing Platform · Visual Overview

How the platform is built & how it tests the website and the app

A separate, independent product that continuously validates the live billing software at ezbillify.com — web, Android and iOS. It never shares code or a database with the billing app; it reaches it only from the outside. Below: the technology stack, the website workflow, the app workflow, and a straight answer on native iOS + Android support — each as its own flowchart.

Will the app have full native support on iOS and Android?

Your direct question, answered.

Yes — full native automation on both Android and iOS.

The platform drives each app at the operating-system level using each vendor's own native automation engine, on both virtual and real hardware. Every native-only feature EzBillify's POS depends on — camera/barcode scanning, biometric login, GPS, push notifications, runtime permissions, install/upgrade, offline↔online sync and receipt printing — is in scope.

Android

Automation engine
Appium 2 + UiAutomator2 driver, plus Maestro flows
Virtual devices
KVM-accelerated emulators, containerised in Kubernetes — scale to many in parallel
Real devices
Self-hosted hardware rack via Android STF

BrowserStack / AWS Device Farm for the OEM matrix (Samsung One UI, Xiaomi MIUI, Pixel…)

.aab / .apk, signature + hash verified on intake

iOS

Virtual devices

Real devices

Cloud burst
BrowserStack / AWS Device Farm for the model matrix (iPhone SE → 15…)

.ipa (real) / .app (simulator), signature + hash verified
⚠ The one real-world caveat

iOS cannot be containerised — Apple's licence requires iOS automation to run on genuine Apple hardware. That's why the device farm includes a macOS rack. It's an infrastructure & ops cost, not a gap in test coverage. Android has no such restriction and runs fully in Kubernetes.

✓ Whatever the app is built with

Because Appium drives the OS layer, this works for native, hybrid, and cross-platform (React Native / Flutter) apps alike — so EzBillify's app is covered regardless of its framework. Note: the platform never builds the app; it tests the signed builds you supply.

One run, end to end — and why it's safe

Every run (web or app) is a durable workflow. The critical property: teardown is guaranteed to run even if a worker crashes, and a reconciliation job then proves no synthetic test data was left behind in production.
